# 予測Appealの条件確認（2026-10-13）

画面の`preview`、通常CPU・おすすめ配置の`createCpuPreview`、実戦の`executeRound`は、配置確定 → `preparePerformance` → 楽曲疲労 → A/C直前処理 → `calcBoth`を共有する。CHARGE CPUの現在ラウンド計算も同じ経路を使う。カード性能・ゲームルール・通常CPUの判断方式は変更していない。

## もともと反映されていた条件

| 条件 | 判定 |
| --- | --- |
| 村井A | BACKS→ステージ登場時に本人を保護。固定Appeal加算ではない |
| 村井C | CENTER時、そのラウンドに登場した味方それぞれ＋1 |
| 村井B | 村井A成立時、免疫対象を味方ステージ5人に広げる |
| 松田好花A | R2以降、両チームのBURST中人数が合計1人以下なら本人＋3 |
| 松田好花C | CENTER時、両チームのBURST中人数が0人なら本人＋3 |
| 好花とJOYFUL LOVE | BURST解除後の人数でA/Cを計算する |
| 松田里奈・中嶋・富田など | 各能力の指定に従い、累計回数／現在BURST中人数を参照する |
| チャージ・履歴・楽曲 | 登場時の消費量、同じ位置、属性、楽曲履歴、現在楽曲、引き継ぎ補正、疲労を使用する |

村井はR1の初期配置とステージ内の移動では登場効果を使わない。候補ごとに前回の`prevPos`から移動を再計算するので、編集中の入れ替え回数を積み増さない。

好花は累計BURST回数や使用済み人数ではなく、現在BURST中の両チーム8人ずつを数える。BACKSも含む。R1のAは不発だがCにはR1の除外がない。

画面は自軍の編集中配置と相手の公開済み配置を使用する。CPUは公開済み状態と自軍候補配置を使う。相手の未確定配置・非公開状態を覗かない。予測で実状態・乱数・チャージを消費しない。

## 未反映だった部分

高速二段階CPUの第1段階では共有準備処理が付けた`negativeShield`を、次の集計で参照していなかった。画面と精密previewはすでに反映していた。

| 不足していた保護 | 修正 |
| --- | --- |
| 楽曲のAppeal減少 | 免疫対象に楽曲減算を加算しない |
| 相手A/B/CのAppeal減少 | 免疫対象に相手由来の負の値を加算しない |
| 相手固定Bの保存済み減算 | `burstDebuff`の初期加算でも免疫を確認する |
| 相手のFRONT位置ボーナス無効 | 免疫中の対象の位置ボーナスを消さない |
| 桜月の疲労ペナルティ倍化 | 免疫中の対象へ楽曲の倍化を適用しない。既存疲労の通常ペナルティは残す |
| 村井Bで広がった免疫 | 対象ごとの免疫を概算でも使用する |

再現例：村井が登場してCENTER、楽曲が夏の近道の場合、精密previewのチームAppealは18、修正前の概算は17、修正後は18。自軍Cの減算は免疫対象にしない。

## CPU方針・互換性

通常CPUは予測獲得ポイント → 勝敗 → 自軍と相手のAppeal差 → 終了時疲労を比較する。発動中のBURSTを反映するが、終了時にBURST条件を満たすための独立加点や次ラウンドのBURST利益は評価しない。CHARGE CPUだけはチャージ系の条件成立・回復・再投入・R7温存を別途評価する。今回はこれらの方針を変更しない。

二段階の第1段階は引き続き概算であり、藤吉コピー・大園の数値変化・小島の軽減など全修正処理の精密な再現は行わない。上位100～300候補の最終評価と実戦は本物のengineを使う。

高速CPUの候補選択が変わり得るため、policyを`two-stage-v2-entry-immunity`に更新した。旧`two-stage-v1`のcheckpointへの追記は拒否し、別の`--out`で新規実行する。通常の全候補評価の結果と再開は維持する。過去の結果は書き換えない。
