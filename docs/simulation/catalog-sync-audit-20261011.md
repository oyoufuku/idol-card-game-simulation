## 楽曲選出

`teams.ts` と `meta-teams.ts` は両方 `songFit` を使う。楽曲の実際のrule・自軍属性/能力・テーマとの効果方向で評価し、タグだけでは選ばない。主タグ追加点も実効果一致が前提。自軍BURST利用と対BURST、移動支援と移動疲労、疲労回復と疲労ペナルティ倍化を分け、自軍への不利益も理由に残す。過去勝率・WARを引数や選出点に使わない。既にこの方針が実装されていたため、評価点・構築方針は維持し、全22曲×9テーマでタグ/仮の勝率/WARを変えても実効果点が変わらないテストを追加した。

## 出力・再確認手順

`summary.json` と各チームに仕様名・定義ファイル・fingerprintを保存する。`summary.catalogSource` と `catalog-snapshot.json` には実行したリポジトリの絶対パス・git commitも記録する。ZIPにGitがなければcommitはnull。全48人・22曲をsnapshotに保存するので、アーキタイプで未採用のカードも確認できる。

```powershell
pnpm.cmd simulate -- --mode archetype --generate-only --seed 1 --out simulation-results/catalog-sync-20261011
```

確認先：

- `simulation-results/catalog-sync-20261011/catalog-snapshot.json`：全48人・22曲・参照元・回答済み裁定。
- `simulation-results/catalog-sync-20261011/summary.json`：実行元・仕様fingerprint。
- `simulation-results/catalog-sync-20261011/archetype/archetypes.json`：27チーム・全メンバー能力・選出score/reason・fingerprint。

今回のfingerprint：`7767efd628c644ba626b48f279d65e08c32cecb0830780fad818dea6e034f76c`。

カード文面もfingerprintの対象なので、旧結果と混在させず新しい出力先を使う。generate-onlyは試合を行わない。
